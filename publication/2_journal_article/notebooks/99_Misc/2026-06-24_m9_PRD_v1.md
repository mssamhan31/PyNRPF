# m9_hybrid PRD v1

Date: 2026-06-24  
Status: exploratory candidate design  
Target role: future main correction model if validation shows clear improvement over `m8_xgb`  
Scope: Dataset Alpha training only; Dataset Beta is held out as the transfer/test set

## 1. Purpose

`m9_hybrid` is a proposed replacement candidate for the current `m8_xgb` correction model. The goal is to improve RPF sign-error detection, especially on Dataset Beta, while keeping the method physically interpretable and suitable for unseen substations.

The current evidence suggests that `m8_xgb` is limited by its representation of the problem. It treats RPF largely as a classification problem over days and intervals. However, the actual manual review task is more structured:

1. Determine whether a site-day contains an RPF sign-error event.
2. If yes, identify one contiguous affected window.
3. Correct only that window by flipping the sign of the raw net load.

`m9_hybrid` should model this structure directly.

## 2. Primary Objective

Maximise day-level F1 on Dataset Beta, using a model trained only on Dataset Alpha.

Secondary objectives:

- Improve interval-level F1 after the day decision.
- Reduce obvious false positives on Beta.
- Reduce obvious false negatives where solar and net load visibly co-move.
- Produce exactly one continuous RPF window per predicted RPF day.
- Preserve interpretability so the method can be explained in the journal article.

## 3. Design Constraints

### 3.1 Training And Evaluation Split

`m9_hybrid` must be trained on Dataset Alpha only.

Dataset Beta is the transfer/test dataset. No Beta training, threshold calibration, or site-specific tuning should be used for the main validation result.

Diagnostic notebooks may inspect Beta errors, but the final candidate model must not learn from Beta labels.

### 3.2 Prediction-Time Information

The model may use the full same-day net load and solar generation profiles. This is acceptable because the task is retrospective oracle correction, not real-time forecasting.

### 3.3 Site Generalisation

The model must be suitable for unseen substations. Avoid per-site thresholds, per-site calibration, or rules that require site-specific labels.

Site-level normalisation is allowed only if it uses unlabeled historical statistics or same-day robust scaling that would be available for a new site.

### 3.4 One-Window Constraint

For now, `m9_hybrid` should output either:

- no RPF for the site-day; or
- exactly one contiguous RPF window between 06:00 and 18:00.

If the training labels contain multiple RPF windows in one day, collapse them into one enclosing window from the first labelled interval to the last labelled interval. This keeps the supervised target aligned with the intended one-window decoder.

## 4. Motivation From Current Diagnostics

The Beta diagnostics suggest that `m8_xgb` has reached a practical limitation:

- Current Beta `m8_xgb` day F1 is around 0.49.
- Global threshold calibration improves only modestly.
- Raw plus site-threshold calibration reached around 0.60 day F1.
- The best site-normalised split-validated variant reached around 0.64 day F1.
- Improvements from calibration and normalisation are real but still limited.
- Remaining errors are site-specific and include visually obvious false positives and false negatives.

This suggests that the main issue is not only threshold choice. The model needs a better problem representation.

Manual review uses shape and physical consistency. In obvious RPF false negatives, solar generation is often smooth and clear-sky-like, while the raw net load follows a similar N-shaped positive pattern rather than becoming negative. In obvious false positives, solar and net load often move in opposite directions, which is normal load behaviour rather than RPF sign-error behaviour.

`m9_hybrid` should encode those clues directly.

## 5. Proposed High-Level Architecture

`m9_hybrid` is a structured hybrid model:

```text
site-day data
  -> preprocessing and robust normalisation
  -> m7-style deterministic geometry candidate generator
  -> optional fallback candidate generator
  -> candidate-window feature extraction
  -> machine-learning candidate scorer
  -> exactly-one-window decoder
  -> no-RPF or one start/end RPF window
```

The key design shift is from interval classification to candidate-window scoring.

Instead of asking, "Is this 15-minute interval RPF?", the model asks:

> "Is this candidate contiguous window the one physically plausible RPF sign-error event for this day?"

## 6. Why This Should Improve On m7 And m8

### 6.1 Improvement Over m7

`m7_dtr` is deterministic and interpretable, but it is too rigid. It uses useful geometric assumptions, yet cannot learn complex combinations of solar shape, net-load shape, seasonal priors, duration, and correction plausibility.

`m9_hybrid` keeps the best part of m7: deterministic candidate geometry. It then adds a learned scorer to decide whether the candidate actually looks like RPF.

Expected benefit:

- fewer false positives from deterministic over-triggering;
- fewer false negatives when candidate geometry is plausible but not perfectly matched to m7 thresholds;
- better transfer because the model uses normalised and physically meaningful candidate features.

### 6.2 Improvement Over m8

`m8_xgb` can learn nonlinear patterns, but it is not structurally constrained enough. It can produce fragmented interval predictions, and its day-level behaviour depends heavily on interval-level outputs and thresholds.

`m9_hybrid` changes the unit of prediction from intervals to candidate windows. This gives the model more global context and enforces the known structure that RPF should usually be one continuous event.

Expected benefit:

- stronger day-level F1;
- fewer fragmented false positives;
- more interpretable start/end boundaries;
- better alignment with manual review logic;
- better ability to exploit same-day shape features.

## 7. Detailed Model Steps

### 7.1 Input Data

For each site-day:

- `substation_id`
- `date`
- 15-minute timestamp sequence
- raw `net_load_MW`
- `solar_MW`
- manual/oracle `label_interval`
- derived `label_day`

The model should operate on the final Alpha/Beta parquet datasets using paper-facing site IDs.

### 7.2 Preprocessing

For each site-day:

1. Restrict candidate logic to review hours, initially 06:00 to 18:00.
2. Keep full-day context for features where useful.
3. Check missingness and finite numeric values.
4. Smooth net load and solar lightly for derivative and shape features.

Potential smoothing options:

- centered rolling median over 3 intervals;
- centered rolling mean over 3 intervals;
- Savitzky-Golay smoothing if available and stable.

Initial recommendation: use a simple centered rolling median or rolling mean first. It is easier to explain and less parameter-heavy.

### 7.3 Robust Normalisation

Normalisation should reduce site scale transfer issues without leaking label information.

Candidate normalisation methods:

1. Site-day robust scaling:
   - `net_load_norm = net_load / max(abs(p95_net_load), epsilon)`
   - `solar_norm = solar / max(p95_solar, epsilon)`

2. Daytime robust range scaling:
   - divide by daytime p95 minus daytime p05;
   - useful when absolute scale varies strongly.

3. Hybrid scale:
   - net load scale from daytime p95 absolute net load;
   - solar scale from daytime p95 solar.

Avoid using raw maximum alone as the default because a single spike can distort the scaling.

Recommended v1:

```text
net_load_scale = max(abs(daytime p95 net load), abs(daytime p05 net load), epsilon)
solar_scale = max(daytime p95 solar, epsilon)
```

Use these to create normalised profiles while preserving raw values for magnitude features.

### 7.4 Training Label Transformation

For each Alpha site-day:

- If no `label_interval=True`, target is no RPF.
- If one or more labelled intervals exist, collapse labels into one enclosing window:
  - `target_start = first labelled timestamp`
  - `target_end = last labelled timestamp`
  - `target_day = True`

This produces one structured target per site-day.

For candidate-window training:

- A candidate is positive if it sufficiently overlaps the collapsed target window.
- A candidate is negative otherwise.

Possible positive definition:

```text
candidate positive if IoU(candidate_window, target_window) >= 0.5
```

Alternative stricter definition:

```text
candidate positive if start/end are within +/- 30 minutes of target start/end
```

Recommended v1:

- Use IoU-based positivity for scorer training.
- Report boundary error separately for diagnostics.

## 8. Candidate Window Generation

The candidate generator is critical. It should produce a small set of plausible windows, not every possible start/end pair.

### 8.1 Primary Generator: m7-Style Geometry

Use the m7 insight that RPF often appears as a positive bounce where net load should have gone negative. The start and end of the affected window are often near left and right local minima or turning points around the suspicious midday shape.

Candidate generation steps:

1. Smooth net load within 06:00 to 18:00.
2. Identify local minima and turning points.
3. Identify positive bumps or N-shaped regions between plausible left and right minima.
4. Generate candidate windows bounded by left/right minima.
5. Filter candidates by duration and solar availability.

Initial duration filters:

- minimum duration: 30 minutes;
- maximum duration: 7 hours;
- candidate must overlap meaningful solar generation.

The exact m7 functions should be inspected and reused where possible so m9 is connected to existing deterministic logic.

### 8.2 Boundary Relaxation

m7-style boundaries may be slightly early or late. For each primary candidate, generate local boundary variants:

- original candidate;
- start shifted by -30, -15, +15, +30 minutes;
- end shifted by -30, -15, +15, +30 minutes;
- only keep valid windows within 06:00 to 18:00 and duration limits.

This lets the ML scorer choose a nearby boundary without exploding the candidate count.

### 8.3 Fallback Generator

Because m7 geometry can miss true RPF days, add a fallback generator based on derivative and co-movement evidence.

Fallback steps:

1. Compute interval evidence:
   - solar magnitude is high;
   - net load is positive but suspicious;
   - smoothed solar derivative and smoothed net-load derivative have the same sign;
   - solar and net load are positively correlated over local windows.
2. Find contiguous high-evidence segments.
3. Keep the top K fallback windows per day.

Recommended v1:

- Generate up to 3 fallback windows per site-day.
- Combine with m7 candidates.
- Deduplicate highly overlapping windows.

### 8.4 Candidate Count Target

Aim for roughly 1 to 20 candidates per site-day.

This is small enough for fast training and inference, and large enough to cover ambiguous boundaries.

## 9. Candidate Features

Each candidate window should be represented by features that are physically meaningful and robust across sites.

### 9.1 Basic Window Features

- start hour
- end hour
- midpoint hour
- duration hours
- month
- day of year
- season indicator
- weekend indicator

### 9.2 Solar Magnitude And Shape Features

Inside candidate:

- max solar
- p95 solar
- mean solar
- solar energy sum
- solar peak time
- solar peak relative to candidate midpoint
- solar clear-sky smoothness score
- solar bell-shape or quadratic fit score
- solar monotonic-up fraction before peak
- solar monotonic-down fraction after peak

Normalised solar features:

- max `solar_norm`
- p95 `solar_norm`
- candidate solar energy as fraction of daily solar energy

### 9.3 Net-Load Magnitude And Shape Features

Inside candidate:

- min raw net load
- max raw net load
- mean raw net load
- p05 raw net load
- p95 raw net load
- net-load range
- net-load peak time
- net-load N-shape score
- net-load smoothness score

Normalised net-load features:

- min `net_load_norm`
- max `net_load_norm`
- mean `net_load_norm`
- p05 and p95 `net_load_norm`

### 9.4 Solar And Net-Load Co-Movement Features

These are probably among the most important features.

For the candidate window:

- Pearson correlation between smoothed solar and smoothed net load.
- Spearman correlation between smoothed solar and smoothed net load.
- Fraction of intervals where solar derivative and net-load derivative have the same sign.
- Mean product of solar derivative and net-load derivative.
- Positive co-movement score during solar ramp-up.
- Positive co-movement score during solar ramp-down.

Physical expectation:

- Normal behaviour: solar increasing tends to reduce net load; derivatives often have opposite signs.
- RPF sign error: raw net load can move with solar; derivatives often have the same sign.

This directly targets the observed obvious FP/FN behaviour.

### 9.5 Correction Plausibility Features

For each candidate, create a hypothetical corrected series:

```text
corrected_net_load = net_load
corrected_net_load[candidate_window] = -net_load[candidate_window]
```

Then compute whether the corrected series looks more plausible than the raw series.

Features:

- smoothness improvement after flipping candidate;
- reduction in midday positive bump;
- corrected series continuity at start boundary;
- corrected series continuity at end boundary;
- corrected net-load correlation with solar;
- corrected net-load derivative anti-correlation with solar derivative;
- corrected midday minimum;
- corrected daily curve U-shape score;
- number of boundary jumps introduced by correction.

Important: these should be features, not hard rules. Some real days are messy.

### 9.6 Contrast Features

Compare inside candidate versus outside candidate:

- inside solar mean minus outside solar mean;
- inside co-movement score minus outside co-movement score;
- inside net-load suspiciousness minus outside suspiciousness;
- inside correction-plausibility gain minus outside gain;
- candidate contains daily solar peak;
- candidate contains daily suspicious net-load peak.

These features help reject days where the entire day is noisy but no specific RPF-like window exists.

### 9.7 m7 Candidate Metadata Features

Because the primary generator is m7-style, expose its diagnostics to the ML scorer:

- candidate source: m7 geometry or fallback;
- m7 rule score;
- left-minimum depth;
- right-minimum depth;
- bounce height;
- distance from solar peak;
- distance between candidate midpoint and net-load peak;
- whether m7 deterministic model would accept the candidate.

This lets the ML model learn when to trust m7.

### 9.8 Missingness And Data Quality Features

- number of missing net-load intervals in day;
- number of missing solar intervals in day;
- number of missing intervals inside candidate;
- flatline indicators;
- zero-solar daytime anomalies;
- duplicated timestamp flags if applicable.

Missingness may explain some hard Beta cases.

## 10. Model Scorer

### 10.1 Recommended v1 Model

Use XGBoost binary classifier as the first scorer:

```text
Input: candidate-window features
Target: candidate is the true/correct RPF window
Output: candidate probability
```

Why XGBoost first:

- already used in m8;
- handles nonlinear feature interactions;
- works well on tabular shape features;
- easier to compare with current workflow;
- supports feature importance diagnostics.

### 10.2 Candidate Training Dataset

For every Alpha site-day:

- Generate candidates using the same candidate generator used at inference.
- Label each candidate against the collapsed target window.
- Include no-RPF days with negative candidates.

Potential issue: no-RPF days may produce zero candidates. For day-level no-RPF training, the model also needs to learn that no strong candidate means no RPF.

Solution:

- Add a day-level meta row or no-candidate summary features; or
- Treat no-candidate days as automatic no-RPF and evaluate them directly; or
- Generate a small number of fallback negative candidates for no-RPF days.

Recommended v1:

- Generate fallback negative candidates on no-RPF days when evidence exists.
- If a day has no candidates, predict no RPF.

### 10.3 Class Imbalance

Candidate-level data will be imbalanced because most candidates are negative.

Use:

- candidate deduplication;
- negative downsampling per day;
- class weights or XGBoost `scale_pos_weight`;
- group-aware validation by held-out Alpha site.

Avoid letting days with many candidate variants dominate training.

Recommended v1:

- Keep all positive candidates.
- Keep at most 10 negative candidates per site-day.
- Use class weighting.

## 11. Decoder

At inference, for each site-day:

1. Generate candidates.
2. Score each candidate.
3. Select the candidate with the highest probability.
4. If no candidate exists, predict no RPF.
5. If best probability is below a global threshold, predict no RPF.
6. Otherwise, output exactly one RPF window from best candidate start to end.

This produces:

- `pred_day`
- `pred_start_time`
- `pred_end_time`
- `pred_interval`
- `candidate_probability`
- candidate diagnostics

### 11.1 Global Threshold

The threshold should be selected using Alpha validation only.

Recommended:

- Use complete Alpha leave-one-station-out validation.
- Select threshold that maximises mean day-level F1.
- Tie-break by higher precision because false positives are worse.
- Then evaluate once on Beta.

No Beta threshold tuning for the main result.

### 11.2 Boundary Refinement

Potential v1.1 extension:

After selecting the best candidate, locally refine start/end by maximising a deterministic plausibility score. Keep this refinement trained/calibrated on Alpha only.

This could improve interval F1 without changing day-level classification much.

## 14. Diagnostics To Include

### 14.1 Candidate Generator Recall

Before training the ML scorer, check whether the candidate generator can even propose the true window.

Metrics:

- percentage of RPF days with at least one candidate overlapping the true window;
- best candidate IoU per RPF day;
- missed RPF days by site/month;
- candidate count per day.

This is critical. If the generator misses many true RPF days, no scorer can recover them.

### 14.2 Candidate Feature Separability

Compare positive and negative candidates by:

- solar peak;
- net-load/solar derivative sign agreement;
- corrected-series smoothness gain;
- candidate duration;
- solar/net-load correlation;
- m7 geometry score.

This checks whether the proposed features create learnable separation.

### 14.3 Error Inspection

For Beta:

- TP examples;
- TN examples;
- FP examples;
- FN examples.

Each Plotly example should show:

- raw net load;
- solar generation;
- manually labelled RPF window;
- m9 predicted RPF window;
- candidate windows considered;
- best candidate probability;
- optionally m7 and m8 predictions for comparison.

## 15. Risks

### 15.1 Candidate Generator Misses True Events

If m7-style geometry misses true RPF windows, the scorer cannot predict them.

Mitigation:

- add fallback derivative/co-movement candidate generator;
- measure candidate generator recall separately;
- allow local boundary shifts around m7 candidates.

### 15.2 Candidate Generator Produces Too Many Negatives

Too many candidate windows can create severe class imbalance and slow training.

Mitigation:

- cap negative candidates per site-day;
- deduplicate overlapping windows;
- use hard-negative mining only after a simple v1 works.

### 15.3 One-Window Constraint May Be Wrong For Some Days

Some labelled days may contain multiple RPF windows.

Mitigation:

- collapse multi-window labels to one enclosing window for v1;
- report how often this happens in Notebook 1;
- revisit multi-window support only if it materially affects F1.

### 15.4 Normalisation May Remove Useful Magnitude Information

Normalisation improves transfer, but raw magnitudes may still matter.

Mitigation:

- include both raw and normalised features;
- use robust scaling rather than raw max scaling;
- report feature importance.

### 15.5 Model Could Overfit Alpha Shape Patterns

Alpha is synthetic/final Alpha and may not fully represent Beta.

Mitigation:

- keep features physically grounded;
- avoid site-specific calibration;
- validate by held-out Alpha sites;
- inspect Beta errors without tuning on Beta.

### 15.6 False Positives Are Costly

The user preference is that false positives are worse than false negatives, while the main target remains F1.

Mitigation:

- optimise Alpha validation F1;
- tie-break thresholds by precision;
- report precision explicitly;
- use correction-plausibility and derivative-consistency features to reject implausible windows.

## 16. Open Design Questions

1. Should the v1 scorer use only XGBoost, or should random forest / logistic regression baselines also be included for interpretability?
2. Should candidate positivity use IoU threshold, start/end tolerance, or both?
3. What min/max duration should be used initially?
4. How much should m7 candidate generation be reused directly versus rewritten cleanly for m9?
5. Should no-candidate days be treated as automatic no-RPF, or should a day-level no-candidate classifier be added?
6. Should boundary refinement be included in v1 or postponed until v1.1?

## 17. Recommended v1 Build Sequence

### Step 1: Measure Label Structure

Use existing Characterisation outputs to confirm:

- how many RPF days have one contiguous window;
- how many have multiple windows;
- typical duration distribution;
- typical start/end times.

This validates the one-window assumption.

### Step 2: Build Candidate Generator

Implement m7-style geometry candidates plus simple fallback candidates.

Output candidate diagnostics before training any ML.

Acceptance criterion:

- high candidate recall on Alpha RPF days;
- reasonable candidate count per site-day.

### Step 3: Build Candidate Features

Implement robust normalisation and candidate-window features.

Start with a compact feature set:

- duration and timing;
- solar magnitude;
- net-load magnitude;
- derivative sign agreement;
- solar/net-load correlation;
- correction smoothness gain;
- m7 metadata.

Add complex shape features only after v1 diagnostics.

### Step 4: Train XGBoost Candidate Scorer

Train on Alpha candidate windows.

Use Alpha complete LOSO for threshold and model validation.

### Step 5: Decode One Window Per Day

Implement global thresholding and exactly-one-window output.

Evaluate day and interval metrics.

### Step 6: Compare Against m7 And m8

Compare `m9_hybrid` with current `m7_dtr` and `m8_xgb` on:

- Alpha LOSO;
- Beta transfer;
- Beta site-level spread;
- FP/FN examples.

### Step 7: Decide Whether To Promote

Promote `m9_hybrid` into the main Notebook 2 workflow only if it clearly improves Beta day-level F1 without unacceptable precision loss and without using Beta calibration.

## 18. Summary Recommendation

`m9_hybrid` should be developed as a structured candidate-window model.

The strongest design is:

```text
m7-style candidate generation
  + robust day/site normalisation
  + physically grounded shape and correction-plausibility features
  + XGBoost candidate-window scorer
  + global threshold selected on Alpha only
  + exactly-one-window decoder
```

This approach directly addresses the limitations observed in m8 diagnostics. It avoids pure interval-by-interval classification, preserves physical interpretability, and aligns closely with how a human reviewer identifies RPF: by looking for one plausible wrong-sign window where raw net load incorrectly co-moves with solar generation.
